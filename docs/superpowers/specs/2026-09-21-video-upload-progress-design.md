# 视频上传进度条设计规格

日期：2026-09-21

## 1. 背景与目标

Movie Harbor 管理后台当前可以上传电影视频和单集视频，但上传期间只显示页面级忙碌状态。大文件或较慢网络下，管理员无法判断请求是否仍在传输，也无法区分“文件仍在上传”和“文件已经传完、后端正在校验并保存”。

本次变更目标：

- 为电影视频和单集视频上传显示真实传输进度。
- 明确区分浏览器上传阶段与服务端校验、保存阶段。
- 保持现有上传接口、媒体校验、原子替换、版本刷新和错误语义不变。
- 复用同一上传进度能力，避免电影与单集编辑器分别实现网络请求逻辑。

本文档是对现有媒体上传与管理后台编辑体验的增量修订；未在本文中修改的媒体格式、安全、生命周期和同步替换规则继续沿用已有规格。

## 2. 范围与非目标

本次覆盖：

- 电影视频上传。
- 单集视频上传。
- 视频替换使用的同一上传流程。

本次不覆盖：

- 海报上传进度。
- 取消、暂停、恢复或断点续传。
- 多文件并发上传、后台上传或离开页面后继续上传。
- 上传速度、剩余时间或已传字节数展示。
- 后端接口、数据库或媒体存储协议变更。

## 3. 界面与状态

进度条采用已确认的“文件区内联”方案，固定显示在对应的 `VideoPicker` 视频文件区域内。它延续管理后台现有深色主题、紧凑表单和细描边视觉，不建立页面级上传卡片，也不把进度嵌入保存或发布按钮。

### 3.1 待上传

管理员选择视频后，界面继续显示：

> 待上传：文件名

此时不显示进度条。只有保存或发布操作真正开始视频请求后，才进入上传状态。

### 3.2 正在上传

浏览器能够计算上传总量时，文件区域显示：

- 文案“正在上传视频…”；
- 0–100 的整数百分比；
- 与百分比一致的确定型进度条。

进度值来自浏览器实际上传事件，不使用计时器或估算值伪造。界面不得显示倒退的百分比；重复或较小的进度事件不降低已经展示的值。

浏览器不能计算上传总量时，显示不确定型进度条和“正在上传视频…”，不显示虚构百分比。

### 3.3 正在校验并保存

当浏览器已完成请求体传输，但完整接口响应尚未返回时：

- 确定型进度条保持 100%；
- 文案切换为“上传完成，正在校验并保存…”；
- 页面继续保持忙碌和禁止重复提交状态。

该状态覆盖后端流式写入收尾、内容校验、媒体替换和数据库提交所需时间，避免管理员把 100% 后的等待误认为页面卡死。

### 3.4 完成与失败

接口成功返回后，界面移除进度条、清空待上传视频，并按现有流程刷新媒体信息和内容版本。

网络中断、超时、HTTP 错误、响应解析错误或服务端校验失败后，界面移除进度状态并显示现有错误提示。待上传文件继续保留，以便管理员修正其他问题或直接重试；现有媒体替换收尾警告和冲突处理规则保持不变。

## 4. 前端架构

### 4.1 共享上传请求

`frontend/packages/api-client` 增加专用于媒体上传的底层请求能力，并使用 `XMLHttpRequest` 发送现有 `FormData` 请求。普通 JSON API 和下载继续使用现有 `fetch` 请求路径，不进行无关替换。

共享上传请求必须继续提供现有客户端边界：

- 只接受受控的同源 `/api` 路径和查询参数；
- 自动携带当前管理员会话的 CSRF 请求头；
- 使用同源 Cookie；
- 不手工设置 multipart `Content-Type`，由浏览器生成边界；
- 将 HTTP 错误、网络错误和 JSON 解析错误映射为现有错误类型；
- 对成功响应继续执行必需响应体检查。

媒体上传公开函数接受可选进度回调。回调只报告展示所需的阶段和进度，不把 `XMLHttpRequest` 实例暴露给页面组件，也不在本次设计中形成取消接口。

### 4.2 上传事件转换

客户端监听上传对象的进度和完成事件：

- 可计算总量时，根据 `loaded / total` 计算并限制为 0–100 的整数；
- 不可计算总量时报告不确定上传状态；
- 请求体传输完成后报告校验保存状态；
- 请求最终成功或失败后，由调用方清理进度状态。

上传事件监听必须在发送请求前注册。传输完成不等于接口成功；页面只有在收到并解析成功响应后才能清除待上传文件或显示成功结果。

### 4.3 页面状态归属

电影编辑器保存当前电影视频的上传状态，并传给共用 `VideoPicker`。

每个 `EpisodeRow` 独立保存自身视频上传状态。只有正在上传的单集显示进度，兄弟单集不显示或复制该状态。现有页面级忙碌锁继续阻止同一页面上的并发写入。

`VideoPicker` 只负责展示当前媒体、待上传文件和上传状态，不负责发起网络请求或解释业务错误。

## 5. 顺序、生命周期与兼容性

电影草稿保存继续按“字段与题材 → 海报 → 视频”的既有顺序执行。如果本次操作同时包含海报和视频，视频进度条只在视频请求开始时出现。

单集继续按“保存字段 → 上传视频 → 可选发布”的顺序执行。上传进度不得改变单集与父剧集版本一致性检查，也不得在上传失败后继续发布。

组件卸载后不得更新页面状态；现有挂载状态保护继续生效。本次不新增离开页面确认或请求取消行为。

后端继续使用 Tokio 流式读取、大小和内容校验、原子替换及同步旧媒体清理。前端进度只描述浏览器向服务器发送请求体的过程，不代表后端已经接受、校验或提交媒体。

## 6. 无障碍与布局

- 确定型进度条提供当前值、最小值和最大值语义。
- 不确定型进度条不声明虚构的当前值。
- 可见状态文本同步提供“正在上传视频”或“上传完成，正在校验并保存”信息，不能只依赖颜色或条宽表达状态。
- 上传状态区域预留稳定位置或采用不引起明显布局跳动的结构。
- 上传期间沿用现有禁用状态，阻止重复保存、发布、选取文件和生命周期操作。

## 7. 错误处理

- 网络、超时和底层请求失败继续转换为客户端网络错误，不暴露浏览器或系统内部细节。
- 非成功 HTTP 响应继续解析结构化错误正文，保留稳定错误码和现有中文提示。
- 无效 JSON 成功响应继续视为响应解析错误。
- 服务端在 100% 后拒绝媒体时，进度状态结束，待上传文件保留，已保存旧媒体保持可见。
- `media_replace_finalization_failed` 等现有“媒体已更新但收尾未完成”语义保持不变；页面在处理该结果后清理进度，并按既有规则刷新或显示警告。
- 版本冲突继续中止后续上传或发布步骤，并要求管理员刷新后重试。

## 8. 测试策略

遵循测试驱动开发：先新增失败测试并确认缺少上传进度行为，再编写最少实现。

### 8.1 共享 API 客户端

- 验证上传请求报告确定进度及传输完成阶段。
- 验证不可计算总量时报告不确定状态。
- 验证上传请求保留同源路径校验、CSRF、Cookie 和 multipart 边界行为。
- 验证成功 JSON、空响应、HTTP 错误、网络错误和无效 JSON 与现有客户端契约一致。
- 验证普通 JSON 请求和下载不改用新上传路径。

### 8.2 管理后台组件

- `VideoPicker` 分别渲染待上传、确定进度、不确定进度和校验保存状态。
- 电影视频上传期间显示真实进度，成功后清除，失败后保留所选文件。
- 单集视频进度只显示在目标单集，兄弟单集不受影响。
- 100% 后先显示校验保存状态，不能提前显示成功或清空文件。
- 上传期间按钮和文件选择保持禁用，避免重复提交。
- 回归验证海报上传、上传顺序、发布、冲突、媒体替换收尾警告及版本刷新。

## 9. 验收标准

- 管理员上传电影视频或单集视频时，可以在对应文件区域看到实际上传进度。
- 可计算进度以整数百分比和进度条同步展示，且显示值不倒退。
- 上传达到 100% 后明确显示“上传完成，正在校验并保存…”，直到接口完成。
- 不可计算总量时使用不确定状态，不伪造百分比。
- 成功后媒体和版本按现有流程刷新；失败后错误清楚、旧媒体不受影响、所选文件可重试。
- 海报上传、后端 API、数据库和媒体存储规则不发生变化。
