# Movie Harbor 管理与公开内容列表分页设计

## 目标

为管理后台内容管理列表增加真正的电影、剧集混合分页和连续序号，并将公开内容目录现有的基础上一页/下一页分页升级为固定每页 20 条的数字页码分页。

本次变更只调整列表查询和展示，不改变电影、剧集、媒体资产的存储模型，不新增数据库迁移，也不改变内容状态流转规则。

## 当前问题

- 管理后台分别请求电影列表和剧集列表，再在浏览器中按“电影在前、剧集在后”拼接。现有接口返回完整详情，剧集列表还包含季和单集，不适合统一排序和数据库分页。
- 管理内容表格没有序号，也没有总数或页码信息。内容数量增长后，一次加载全部记录会增加数据库、网络和渲染成本。
- 公开目录后端已经支持 `page` 和 `size`，前端也使用 URL 保存页码，但当前固定请求每页 25 条，只显示上一页、当前页和下一页，无法直接跳转到指定页。

## 方案选择

### 管理列表

采用新的统一管理内容接口，由 PostgreSQL 使用 `UNION ALL` 合并电影和剧集的公共列表字段，再完成统一筛选、稳定排序、计数和分页。

不采用前端分别请求后再合并的方案，因为前端无法只取得全局第 N 页，必须过量读取两类数据；也不采用后端分别加载完整对象后在内存中分页，因为会继续加载列表不需要的题材、视频、季和单集数据。

### 公开列表

保留现有 `/api/catalog` 分页协议和 URL 驱动状态，只将公开站固定请求数量从 25 调整为 20，并增加数字页码窗口。桌面端五列布局下，每页形成四行内容卡片。

## 统一管理内容接口

新增：

```text
GET /api/admin/contents
```

查询参数：

- `kind`：`all`、`movie` 或 `series`，省略时为 `all`。
- `status`：`draft`、`published` 或 `archived`，省略时不过滤状态。
- `name`：按现有管理列表规则匹配名称，空白值按未提供处理。
- `page`：从 1 开始的正整数，省略时为 1。
- 页面大小由服务端固定为 20，不提供 `size` 参数。

响应使用轻量列表结构：

```json
{
  "page": 1,
  "size": 20,
  "total": 53,
  "items": [
    {
      "id": "内容 ID",
      "kind": "movie",
      "name": "内容名称",
      "status": "published",
      "version": 3,
      "created_at": "RFC 3339 时间",
      "poster_url": "/media/受控文件标识"
    }
  ]
}
```

`poster_url` 在没有海报时为 `null`。列表响应不包含简介、题材、视频、季或单集；打开编辑或查看页时继续通过现有电影、剧集详情接口读取完整对象。操作按钮仍由内容状态映射得到，实际状态约束继续由后端执行。

原有 `/api/admin/movies` 和 `/api/admin/series` 接口暂时保留，避免影响既有调用。

## 查询、排序与一致性

电影和剧集先投影为相同字段，再应用统一的类型、状态和名称筛选。全局排序固定为：

1. `created_at DESC`
2. `kind ASC`
3. `id ASC`

后两个字段用于消除相同创建时间下的不确定顺序，保证翻页结果稳定。

总数查询和当前页查询在同一个只读事务快照中执行。`page` 为零、非整数或超过服务端安全上限时返回 `400`；合法但超过最后一页的请求返回原页码、正确总数和空 `items`，由前端按对应场景修正页码。

## 管理后台状态与交互

管理列表的筛选条件、当前页码和刷新版本提升到管理后台 `App` 层。进入电影或剧集编辑/查看页再返回时，原筛选条件和页码仍然保留。

- 每页固定 20 条，不提供页面大小选择器。
- 执行新查询或改变类型、状态、名称筛选时回到第 1 页。
- 点击页码、上一页或下一页时保留筛选条件，只更新目标页。
- 发布、归档、原样发布、转为草稿等列表操作成功后刷新当前页。
- 删除内容后返回列表并刷新当前页；如果当前页为空且页码大于 1，则自动请求上一页，直到得到有效页或回到第 1 页。
- 列表请求期间禁用重复翻页。请求失败时保留当前已展示的数据和页码，并显示中文错误提示。
- 沿用现有请求世代保护：较早发出的筛选、翻页或刷新响应不能覆盖较新的响应。

## 管理列表序号

表格在海报列之前增加“序号”列。序号按当前筛选结果跨页连续计算：

```text
(当前页 - 1) × 20 + 当前页内索引 + 1
```

因此第 1 页显示 1–20，第 2 页显示 21–40。改变筛选条件后，新的结果集从 1 重新编号。序号只由前端根据页码和行位置计算，不写入数据库，也不作为内容身份标识。

## 分页栏

管理列表采用已确认的 A 布局：表格下方同一行左侧显示“共 N 条 · 第 X/Y 页”，右侧显示上一页、数字页码和下一页；窄屏时允许自然换行。

管理后台与公开站共享纯页码窗口计算逻辑，但分别使用各自的页面样式。页码规则为：

- 总页数不超过 7 时显示全部页码。
- 总页数较多时显示首页、末页、当前页附近页码和省略号，例如“1 … 4 5 6 … 12”。
- 当前页设置高亮和 `aria-current="page"`。
- 上一页和下一页在边界处禁用。
- 加载过程中保留分页栏尺寸，避免页面明显跳动。

## 公开目录分页

公开目录继续从 URL 解析 `kind`、`q` 和 `page`，并调用现有 `/api/catalog` 接口：

- 前端固定发送 `size=20`。
- 搜索或切换电影/剧集类型时移除页码参数，回到第 1 页。
- 点击数字页码或前后页时更新 URL，例如 `?page=2`，因此刷新、浏览器前进和后退都能恢复页码。
- 翻页成功后焦点回到目录标题，沿用现有无障碍行为。
- 通过 URL 进入超过总页数的合法页码时，使用 `replace` 导航到最后一个有效页；总数为零时规范到第 1 页。
- 公开站只复用页码窗口逻辑，分页栏视觉继续服从公开站现有主题。

## 错误与边界

- 前端把缺失、非数字、小于 1 或超过前端安全上限的页码解析为第 1 页；后端仍独立验证参数。
- 总页数使用 `max(1, ceil(total / size))` 展示，空结果显示第 1/1 页。
- 管理列表因删除或并发变化落入空页时向前回退；公开列表的 URL 越界时规范到最后有效页。
- 分页修正不得形成重复请求循环；只有响应证明当前页越界时才触发一次目标页变更。
- 现有详情、状态转换和删除接口保持不变，分页功能不放宽任何权限或状态约束。

## 测试策略

后端测试覆盖：

- 电影和剧集混合后的全局排序与相同时间下的稳定顺序。
- `kind`、`status`、`name` 单独和组合筛选。
- 固定 20 条分页、正确 `total`、第一页、中间页、末页和越界空页。
- 非法页码拒绝，以及轻量响应不包含详情层级。

管理后台组件测试覆盖：

- 新统一接口的查询参数和过期响应保护。
- 跨页连续序号。
- 查询重置到第 1 页，翻页保留筛选条件。
- 状态转换后保留当前页。
- 删除末条后回到上一页。
- 数字页码窗口、省略号、禁用状态和 `aria-current`。

公开站组件测试覆盖：

- 固定发送 `size=20`。
- 数字页码更新 URL，搜索和类型切换清除页码。
- 浏览器历史恢复页码、越界页规范化和翻页后的焦点管理。
- 请求失败与快速切页时不展示过期响应。

端到端测试使用隔离数据验证超过 20 条内容时，管理列表和公开目录都能跨页访问预期记录。完成前执行项目约定中与 Rust、前端构建、Node 契约测试、Docker Compose 和 Playwright 相关的完整验证集合。
